# Настройка маршрутизации для YouTubeCDN

Пошаговая инструкция по выборочной маршрутизации видео YouTube через Xray в OPNsense. Unbound остаётся основным DNS-сервером для клиентов, Dnsmasq собирает адреса из DNS-ответов для `googlevideo.com`, а правило файрвола отправляет соединения к этим адресам в `VPN_GW`. Для остальных соединений действуют существующие правила, включая обычный выход через WAN для игрового трафика.

## Когда пригодится эта схема

Симптом характерный. Страница YouTube и превью загружаются, а запросы `videoplayback` к поддоменам `googlevideo.com` зависают или завершаются таймаутом. Через браузер, подключённый напрямую к SOCKS того же Xray, ролик играет.

При выборочной маршрутизации OPNsense сравнивает IP назначения с таблицами файрвола. Если адрес очередного CDN отсутствует в алиасах правила с VPN-шлюзом, соединение может попасть под общее правило выхода через WAN. При смене VPN-профиля YouTube может выбрать другой CDN, чей IP уже входит в один из алиасов.

Google Global Cache позволяет провайдерам раздавать контент из собственных сетей. Поэтому статический список сетей Google может пропустить видеосервер, на котором фактически запрашивается ролик. Динамический алиас берёт адреса из DNS-ответов для `googlevideo.com` и его поддоменов. [Google Global Cache](https://support.google.com/interconnect/answer/9058809)

## Схема и исходные настройки

```text
DNS для googlevideo.com и его поддоменов
Клиент → Unbound :53 → Dnsmasq :1054 → локальный DoH-клиент :1053
                               └─ добавляет IP в YT_CDN

Видеопоток
Клиент → правило с YT_CDN → VPN_GW → нода Xray
```

Настройка рассчитана на рабочий туннель Xray и Unbound как основной DNS. Имена, порты и адреса в таблице приведены для примера. В настройках и командах использовать свои значения.

| Компонент | Значение в примере |
| --- | --- |
| DNS для клиентов | Unbound на OPNsense, порт `53` |
| Локальный DoH-клиент | `127.0.0.1:1053`. Использовать адрес и порт существующего локального резолвера. |
| Dnsmasq | `127.0.0.1:1054`. Выбрать свободный порт для запросов от Unbound. |
| Входящий интерфейс клиентов | `LAN_CLIENTS`. Подставить имя интерфейса клиентской сети. |
| Шлюз для прокси-трафика | `VPN_GW`. Выбрать существующий шлюз Xray. |
| Интерфейс туннеля | `VPN_TUN_IF`. Подставить системное имя интерфейса для захвата пакетов. |
| SOCKS Xray на OPNsense | `127.0.0.1:1080`. Подставить порт SOCKS при дополнительной проверке через SSH. |
| Алиас для адресов CDN | `YT_CDN`. Использовать выбранное имя в Dnsmasq, правиле файрвола и командах `pfctl`. |

Инструкция охватывает IPv4-маршрутизацию. Для DNS-проверок используется публичное имя `redirector.googlevideo.com`. При диагностике ролика подставить имя его CDN. Адрес `203.0.113.42` в примерах относится к диапазону для документации. В командах проверки маршрута подставить фактический адрес из браузера. [RFC 5737](https://www.rfc-editor.org/rfc/rfc5737.html)

## 1. Проверить DNS перед настройкой

При использовании локального DoH-клиента проверить его общую запись в **Services → Unbound DNS → Query Forwarding**.

| Поле | Значение |
| --- | --- |
| Enabled | Включено |
| Domain | Пусто |
| Server IP | `127.0.0.1` |
| Port | `1053` |

На OPNsense проверить локальный резолвер. Для диагностики конкретного ролика подставить имя из **DevTools → Network → videoplayback → Request URL**, без `https://` и пути.

```sh
drill -p 1053 redirector.googlevideo.com @127.0.0.1 A
```

Ожидаемый ответ — `rcode: NOERROR` и запись `A`. CDN может возвращать цепочку `CNAME → A`. Если локальный DoH-клиент слушает другой порт, использовать этот порт в проверке и в настройке upstream Dnsmasq. Если Unbound сам разрешает DNS без локального DoH, перейти к созданию алиаса и использовать вариант с внешним DNS в шаге 3. [Unbound Query Forwarding](https://docs.opnsense.org/manual/unbound.html#query-forwarding)

## 2. Создать алиас YT_CDN

Открыть **Firewall → Aliases → Add** и задать параметры.

| Поле | Значение |
| --- | --- |
| Enabled | Включено |
| Name | `YT_CDN` |
| Type | `External (advanced)` |
| Expire | По необходимости, в секундах |
| Description | `Адреса CDN YouTube из DNS-ответов` |

Нажать **Save → Apply**. Алиас заполнится после первых подходящих DNS-запросов. При заданном **Expire** неиспользуемые адреса будут удаляться со временем. [Dnsmasq Firewall Alias](https://docs.opnsense.org/manual/dnsmasq.html#firewall-alias-ipset)

## 3. Настроить Dnsmasq

В **Services → Dnsmasq DNS & DHCP → General** установить флажок **Enable** и указать `1054` в **Listen Port**, затем нажать **Apply**. Если Dnsmasq используется только для этой задачи, в **Interface** достаточно выбрать `LAN_CLIENTS`. Dnsmasq также принимает запросы на IPv4 loopback, когда указаны интерфейсы. Unbound из всех клиентских сетей будет обращаться к нему через loopback. Если Dnsmasq уже обслуживает DHCP, оставить выбранными интерфейсы с его DHCP-диапазонами. [Настройки Dnsmasq](https://docs.opnsense.org/manual/dnsmasq.html)

В **Services → Dnsmasq DNS & DHCP → Domains → Add** добавить запись.

| Поле | Значение |
| --- | --- |
| Domain | `googlevideo.com` |
| IP address | `127.0.0.1` |
| Port | `1053` |
| Source IP | Пусто |
| Firewall Alias | `YT_CDN` |

В записи достаточно `googlevideo.com`. Dnsmasq применяет её и к поддоменам. Нажать **Save → Apply**. Upstream на `1053` должен сам отправлять запросы внешнему резолверу, иначе образуется цикл через Unbound.

Сразу проверить Dnsmasq напрямую.

```sh
drill -p 1054 redirector.googlevideo.com @127.0.0.1 A
```

Если появился `NOERROR` с записью `A`, проверить, добавился ли этот IP в алиас. Команды `pfctl` и `tcpdump` на OPNsense выполнять от root.

```sh
pfctl -t YT_CDN -T show
```

Если локального DoH-клиента нет, в поле **IP address** можно указать внешний DNS с портом `53`. Такой запрос идёт без шифрования. Перед применением подставить адрес выбранного сервера вместо `PUBLIC_DNS_IP` и проверить его доступность с OPNsense.

```sh
drill -p 53 redirector.googlevideo.com @PUBLIC_DNS_IP A
```

## 4. Направить googlevideo.com из Unbound в Dnsmasq

В **Services → Unbound DNS → Query Forwarding → Add** добавить и применить отдельное правило.

| Поле | Значение |
| --- | --- |
| Enabled | Включено |
| Domain | `googlevideo.com` |
| Server IP | `127.0.0.1` |
| Port | `1054` |

Правило с конкретным доменом охватывает и его поддомены. При настройке с локальным DoH строка с пустым **Domain** указывает на порт `1053` и обслуживает остальные запросы. Два порта в этой схеме выполняют разные задачи. Unbound отправляет DNS для видео в Dnsmasq на `1054`, а Dnsmasq обращается к DoH-клиенту на `1053`. [Unbound Query Forwarding](https://docs.opnsense.org/manual/unbound.html#query-forwarding)

Запросить тот же домен через Unbound.

```sh
drill -p 53 redirector.googlevideo.com @127.0.0.1 A
```

Если Unbound слушает только адрес интерфейса, подставить IP OPNsense в сети `LAN_CLIENTS` после `@`. Для проверки с клиентского ПК подходит `nslookup`. В команде заменить `OPNSENSE_LAN_IP` на DNS-адрес, который должен использовать клиент.

```sh
nslookup redirector.googlevideo.com OPNSENSE_LAN_IP
```

## 5. Добавить YT_CDN в правило маршрутизации

В **Firewall → Rules → LAN_CLIENTS** найти существующее входящее правило со шлюзом `VPN_GW`, расположенное выше общего разрешающего правила с выходом через WAN. Если поле **Destination** поддерживает несколько алиасов, добавить `YT_CDN` к уже выбранным. Тогда новый алиас унаследует протоколы, порты и источник этого правила.

Для ограничения только TCP/UDP на порту `443` создать отдельное правило.

| Поле | Значение |
| --- | --- |
| Action | `Pass` |
| Quick / Direction | Включено / `In` |
| Version | `IPv4` |
| Protocol | `TCP/UDP` |
| Source | `LAN_CLIENTS net`, либо адрес тестового ПК с маской `/32` |
| Destination | `YT_CDN` |
| Invert Destination | Выключено |
| Destination port | `HTTPS (443)` |
| Gateway | `VPN_GW` |

Разместить правило ниже правил DNS и локальных ограничений, выше общего разрешающего правила с выходом через WAN. Нажать **Save → Apply**. Для других клиентских сетей добавить алиас в подходящие правила на их входящих интерфейсах. У каждой сети должны работать DNS-запросы к Unbound и своё правило с нужным шлюзом. [Правила файрвола OPNsense](https://docs.opnsense.org/manual/firewall_generic.html)

## 6. Проверить воспроизведение и фактический маршрут

1. Для чистой проверки отключить VPN-клиент или SOCKS-прокси на тестовом устройстве и выключить временные правила для всего трафика на порту `443`, если они создавались для диагностики. Клиент должен использовать DNS OPNsense. При внешнем Secure DNS в браузере запросы идут мимо Unbound и не пополняют этот алиас.
2. Открыть YouTube в обычном браузере. В **DevTools → Network** найти успешный запрос `videoplayback` с кодом `200` или `206`. Записать **Remote Address** без порта. Параметр `ip=` в подписанном URL — часть запроса YouTube. Адрес сетевого назначения следует брать из **Remote Address**.
3. Проверить принадлежность IP алиасу. Заменить адрес в командах на текущий IPv4 видеосервера.

```sh
pfctl -t YT_CDN -T test 203.0.113.42
pfctl -t YT_CDN -T show
```

Для первого вызова ожидается `1/1 addresses match`. В веб-интерфейсе содержимое таблицы видно в **Firewall → Diagnostics → Aliases**.

Подставить системное имя туннеля вместо `VPN_TUN_IF` и фактический IPv4 вместо `203.0.113.42`. Список имён интерфейсов показывает `ifconfig -l`. Запустить захват и открыть ролик заново либо перемотать его. Если CDN сменился, обновить адрес фильтра. Остановить захват можно с помощью `Ctrl+C`.

```sh
tcpdump -ni VPN_TUN_IF 'host 203.0.113.42 and port 443'
```

Воспроизведение вместе с пакетами на интерфейсе туннеля подтверждает маршрут. Если **Remote Address** содержит IPv6, для этого соединения понадобится отдельный IPv6-маршрут с поддержкой IPv6 в туннеле. [Диагностика файрвола OPNsense](https://docs.opnsense.org/manual/diagnostics_firewall.html)

## Диагностика

### Домен перестал резолвиться

Сравнить ответ одного и того же имени на трёх портах.

```sh
drill -p 1053 redirector.googlevideo.com @127.0.0.1 A
drill -p 1054 redirector.googlevideo.com @127.0.0.1 A
drill -p 53 redirector.googlevideo.com @127.0.0.1 A
```

| Результат | Что проверить |
| --- | --- |
| `1053` отвечает, `1054` возвращает `SERVFAIL` | В **Dnsmasq → Domains** проверить upstream `127.0.0.1:1053`. Применить запись и повторить запрос напрямую к Dnsmasq. |
| `1054` не отвечает | Проверить **Enable**, **Listen Port** и выбранный интерфейс в Dnsmasq. |
| `1054` отвечает, `53` возвращает ошибку | Проверить отдельную запись в **Unbound → Query Forwarding**. Если Unbound слушает DNS только на LAN-адресе, использовать этот адрес в проверке. |
| Ошибка уже на `1053` | Проверить локальный DoH-клиент и его внешний резолвер. |

Если локальный DoH возвращает `NOERROR` с записью `A`, а прямой запрос к Dnsmasq долго ждёт и завершается `SERVFAIL`, проверить, куда Dnsmasq отправляет запрос. Например, при недоступном внешнем DNS на порту `53` можно указать отвечающий локальный DoH-резолвер и повторить проверку на порту Dnsmasq.

Проверить, слушает ли Dnsmasq, и увидеть обмен с DoH-клиентом можно такими командами. Во время захвата повторить запрос к Dnsmasq в другом терминале.

```sh
sockstat -4 -l -p 1054
tcpdump -ni lo0 'port 1053 or port 1054'
```

### DNS отвечает, но алиас пустой

Проверить тип `External (advanced)`, выбранный **Firewall Alias** в **Dnsmasq → Domains** и применение изменений. Сделать новый запрос к поддомену через Unbound и ещё раз посмотреть таблицу. У браузера может быть старый DNS-ответ в кеше. Если браузер использует внешний DoH, сравнить его адрес назначения с ответом локального Unbound.

### IP есть в алиасе, но потока в туннеле нет

Проверить входящий интерфейс, источник, порядок правил и выбранный gateway. Запустить новое соединение, чтобы исключить сохранённое состояние старого соединения. При необходимости найти состояние конкретного потока в **Firewall → Diagnostics → States**. Для проверяемого запроса сравнить фактический IP назначения и версию IP с полями правила. [OPNsense Firewall Diagnostics](https://docs.opnsense.org/manual/diagnostics_firewall.html)

### Сравнение с исходными алиасами

Чтобы понять, какое правило охватывает CDN, проверить IP по каждому алиасу назначения в правиле с VPN-шлюзом. В команде заменить `VPN_DESTINATIONS` на имя проверяемого алиаса и подставить фактический IP. `pfctl -T test` учитывает и одиночные адреса, и попадание в подсеть.

```sh
pfctl -t VPN_DESTINATIONS -T test 203.0.113.42
```

Если URL статического списка добавлялся в алиас только для YouTube, после проверки `YT_CDN` его можно удалить из этого алиаса и проверить остальные маршруты.

### Проверка через SOCKS того же Xray

Эта проверка полезна, когда нужно отделить работу VPN от правил на входе клиентской сети. При доступном SSH-форвардинге открыть на ПК локальный порт до SOCKS на OPNsense. В команду подставить SSH-логин, LAN-адрес роутера и порт его SOCKS-прокси. Если локальный порт `1081` занят, заменить его в обеих командах.

```sh
ssh -N -o ExitOnForwardFailure=yes \
  -L 127.0.0.1:1081:127.0.0.1:1080 USER@OPNSENSE_LAN_IP
```

Оставить SSH-соединение открытым. На Linux в другом терминале запустить отдельный Chrome с SOCKS и открыть тот же ролик.

```sh
google-chrome --user-data-dir="$(mktemp -d)" \
  --proxy-server="socks5://127.0.0.1:1081" \
  --disable-quic https://www.youtube.com/
```

Если ролик играет, цепочка Xray передаёт видео по TCP через SOCKS. Браузер в этом режиме передаёт имя через SOCKS, поэтому DNS и выбор CDN могут отличаться от обычного запуска. Проверка `curl` на корне CDN по пути `/` может вернуть `HTTP 404` даже при исправном соединении. Воспроизведение проверяется реальным `videoplayback`.

## Как откатить изменения

1. В **Unbound → Query Forwarding** выключить только запись `googlevideo.com → 127.0.0.1:1054` и нажать **Apply**. Запросы к домену вернутся к общей схеме DNS.
2. Убрать `YT_CDN` из правила с `VPN_GW` или выключить отдельное правило для этого алиаса. Применить настройки.
3. Если Dnsmasq включался специально для этого алиаса, его можно отключить в **General** после отката перенаправления.
