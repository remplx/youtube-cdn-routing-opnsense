# Настройка маршрутизации для YouTubeCDN

Пошаговая инструкция по выборочной маршрутизации видео YouTube через Xray в OPNsense. Unbound остаётся основным DNS-сервером для клиентов, Dnsmasq собирает адреса из DNS-ответов для `googlevideo.com`, а правило файрвола отправляет соединения к этим адресам в `XRAYOUT`. Для остальных соединений действуют существующие правила, включая обычный выход через WAN для игрового трафика.

## Когда пригодится эта схема

Симптом характерный. Страница YouTube и превью загружаются, а запросы `videoplayback` к поддоменам `googlevideo.com` зависают или завершаются таймаутом. Через браузер, подключённый напрямую к SOCKS того же Xray, ролик играет.

При выборочной маршрутизации OPNsense сравнивает IP назначения с таблицами файрвола. Если адрес очередного CDN отсутствует в `PROXYDomains` и `runetfreedomBlockList`, соединение может попасть под общее правило выхода через WAN. Рабочий профиль VPN может получить другой CDN, чей IP уже входит в один из алиасов.

В нашем случае `rr1---sn-35153iuxa-unxk.googlevideo.com` резолвился в `178.91.255.76` из сети Казахтелекома. В обеих таблицах был результат `0/1 addresses match`. Адреса других видеосерверов, `173.194.19.103` и `74.125.166.200`, покрывались списком `re-filter.txt`. Google Global Cache позволяет провайдерам раздавать контент из собственных сетей, поэтому одного списка сетей Google или адресов одной страны для такой маршрутизации мало. [RIPE](https://rdap.db.ripe.net/ip/178.91.255.76) · [Google Global Cache](https://support.google.com/interconnect/answer/9058809) · [RunetFreedom](https://github.com/runetfreedom/russia-blocked-geoip)

## Схема и исходные настройки

```text
DNS для googlevideo.com и его поддоменов
Клиент → Unbound :53 → Dnsmasq :53053 → локальный DoH-клиент :5353
                               └─ добавляет IP в YouTubeCDN

Видеопоток
Клиент → правило с YouTubeCDN → XRAYOUT → нода Xray
```

Настройка рассчитана на рабочий туннель Xray и Unbound как основной DNS. В команды и настройки следует подставить значения из своей системы.

| Компонент | Значение в примере |
| --- | --- |
| DNS для клиентов | Unbound на OPNsense, порт `53` |
| Локальный DoH-клиент | `127.0.0.1:5353`, принимает обычные DNS-запросы локально и отправляет их дальше по DoH |
| Входящий интерфейс клиентов | `PCmain` |
| Шлюз для прокси-трафика | `XRAYOUT - 10.255.0.2` |
| Интерфейс туннеля | `proxytun2socks0` |
| SOCKS Xray на OPNsense | `127.0.0.1:10808` |

Инструкция охватывает IPv4-маршрутизацию. В нашем случае туннель подключался к ноде Remnawave по VLESS + XHTTP + TLS через Nginx.

## 1. Проверить DNS перед настройкой

При использовании локального DoH-клиента проверить его общую запись в **Services → Unbound DNS → Query Forwarding**.

| Поле | Значение |
| --- | --- |
| Enabled | Включено |
| Domain | Пусто |
| Server IP | `127.0.0.1` |
| Port | `5353` |

На OPNsense проверить локальный резолвер. В командах ниже используется реальный CDN из диагностики. Если адрес изменился, подставить свежее имя из **DevTools → Network → videoplayback → Request URL**, без `https://` и пути.

```sh
drill -p 5353 rr1---sn-35153iuxa-unxk.googlevideo.com @127.0.0.1 A
```

Ожидаемый ответ — `rcode: NOERROR` и запись `A`. CDN может возвращать цепочку `CNAME → A`. Если локальный DoH-клиент слушает другой порт, использовать этот порт в проверке и в настройке upstream Dnsmasq. Если Unbound сам разрешает DNS без локального DoH, перейти к созданию алиаса и использовать вариант с внешним DNS в шаге 3. [Unbound Query Forwarding](https://docs.opnsense.org/manual/unbound.html#query-forwarding)

## 2. Создать алиас YouTubeCDN

Открыть **Firewall → Aliases → Add** и задать параметры.

| Поле | Значение |
| --- | --- |
| Enabled | Включено |
| Name | `YouTubeCDN` |
| Type | `External (advanced)` |
| Expire | `86400` секунд |
| Description | `Адреса CDN YouTube из DNS-ответов` |

Нажать **Save → Apply**. Алиас заполнится после первых подходящих DNS-запросов. Значение **Expire** позволяет таблице со временем очищать неиспользуемые адреса. [Dnsmasq Firewall Alias](https://docs.opnsense.org/manual/dnsmasq.html#firewall-alias-ipset)

## 3. Настроить Dnsmasq

В **Services → Dnsmasq DNS & DHCP → General** установить флажок **Enable** и указать `53053` в **Listen Port**, затем нажать **Apply**. Если Dnsmasq используется только для этой задачи, в **Interface** достаточно выбрать `PCmain`. Dnsmasq также принимает запросы на IPv4 loopback, когда указаны интерфейсы. Unbound из всех клиентских сетей будет обращаться к нему через loopback. Если Dnsmasq уже обслуживает DHCP, оставить выбранными интерфейсы с его DHCP-диапазонами. [Настройки Dnsmasq](https://docs.opnsense.org/manual/dnsmasq.html)

В **Services → Dnsmasq DNS & DHCP → Domains → Add** добавить запись.

| Поле | Значение |
| --- | --- |
| Domain | `googlevideo.com` |
| IP address | `127.0.0.1` |
| Port | `5353` |
| Source IP | Пусто |
| Firewall Alias | `YouTubeCDN` |

В записи достаточно `googlevideo.com`. Dnsmasq применяет её и к поддоменам. Нажать **Save → Apply**. Upstream на `5353` должен сам отправлять запросы внешнему резолверу, иначе образуется цикл через Unbound.

Сразу проверить Dnsmasq напрямую.

```sh
drill -p 53053 rr1---sn-35153iuxa-unxk.googlevideo.com @127.0.0.1 A
```

Если появился `NOERROR` с записью `A`, проверить, добавился ли этот IP в алиас. Команды `pfctl` и `tcpdump` на OPNsense выполнять от root.

```sh
pfctl -t YouTubeCDN -T show
```

Если локального DoH-клиента нет, в поле **IP address** можно указать внешний DNS, например `1.1.1.1`, с портом `53`. Такой запрос идёт без шифрования. Перед применением проверить доступность выбранного сервера с самого OPNsense. В описанном случае рабочим вариантом оказался локальный DoH на `5353`.

```sh
drill -p 53 rr1---sn-35153iuxa-unxk.googlevideo.com @1.1.1.1 A
```

## 4. Направить googlevideo.com из Unbound в Dnsmasq

В **Services → Unbound DNS → Query Forwarding → Add** добавить и применить отдельное правило.

| Поле | Значение |
| --- | --- |
| Enabled | Включено |
| Domain | `googlevideo.com` |
| Server IP | `127.0.0.1` |
| Port | `53053` |

Правило с конкретным доменом охватывает и его поддомены. При настройке с локальным DoH строка с пустым **Domain** указывает на порт `5353` и обслуживает остальные запросы. Два порта в этой схеме выполняют разные задачи. Unbound отправляет DNS для видео в Dnsmasq на `53053`, а Dnsmasq обращается к DoH-клиенту на `5353`. [Unbound Query Forwarding](https://docs.opnsense.org/manual/unbound.html#query-forwarding)

Запросить тот же домен через Unbound.

```sh
drill -p 53 rr1---sn-35153iuxa-unxk.googlevideo.com @127.0.0.1 A
```

Если Unbound слушает только адрес интерфейса, подставить IP OPNsense в сети `PCmain` после `@`. Для проверки с клиентского ПК подходит `nslookup`. В команде заменить `OPNSENSE_LAN_IP` на DNS-адрес, который должен использовать клиент.

```sh
nslookup rr1---sn-35153iuxa-unxk.googlevideo.com OPNSENSE_LAN_IP
```

## 5. Добавить YouTubeCDN в правило маршрутизации

В **Firewall → Rules → PCmain** найти существующее входящее правило с gateway `XRAYOUT`, расположенное выше общего разрешающего правила с выходом через WAN. Если поле **Destination** поддерживает несколько алиасов, добавить `YouTubeCDN` рядом с `PROXYDomains` и `runetfreedomBlockList`. Тогда новый алиас унаследует протоколы, порты и источник этого правила.

Для ограничения только TCP/UDP на порту `443` создать отдельное правило.

| Поле | Значение |
| --- | --- |
| Action | `Pass` |
| Quick / Direction | Включено / `In` |
| Version | `IPv4` |
| Protocol | `TCP/UDP` |
| Source | `PCmain net`, либо адрес тестового ПК с маской `/32` |
| Destination | `YouTubeCDN` |
| Invert Destination | Выключено |
| Destination port | `HTTPS (443)` |
| Gateway | `XRAYOUT - 10.255.0.2` |

Разместить правило ниже правил DNS и локальных ограничений, выше общего разрешающего правила с выходом через WAN. Нажать **Save → Apply**. Для других клиентских сетей добавить алиас в подходящие правила на их входящих интерфейсах. У каждой сети должны работать DNS-запросы к Unbound и своё правило с нужным шлюзом. [Правила файрвола OPNsense](https://docs.opnsense.org/manual/firewall_generic.html)

## 6. Проверить воспроизведение и фактический маршрут

1. Для чистой проверки выключить Happ, тестовый SOCKS в браузере и временное правило, которое перенаправляло весь порт `443`. Клиент должен использовать DNS OPNsense. При внешнем Secure DNS в браузере запросы идут мимо Unbound и не пополняют этот алиас.
2. Открыть YouTube в обычном браузере. В **DevTools → Network** найти успешный запрос `videoplayback` с кодом `200` или `206`. Записать **Remote Address** без порта. Параметр `ip=` в подписанном URL — часть запроса YouTube. Адрес сетевого назначения следует брать из **Remote Address**.
3. Проверить принадлежность IP алиасу. Заменить адрес в командах на текущий IPv4 видеосервера.

```sh
pfctl -t YouTubeCDN -T test 178.91.255.76
pfctl -t YouTubeCDN -T show
```

Для первого вызова ожидается `1/1 addresses match`. В веб-интерфейсе содержимое таблицы видно в **Firewall → Diagnostics → Aliases**.

Запустить захват и открыть ролик заново либо перемотать его. Если CDN сменился, обновить адрес фильтра. Остановить захват можно с помощью `Ctrl+C`.

```sh
tcpdump -ni proxytun2socks0 'host 178.91.255.76 and port 443'
```

Воспроизведение вместе с пакетами на интерфейсе туннеля подтверждает маршрут. Если **Remote Address** содержит IPv6, для этого соединения понадобится отдельный IPv6-маршрут с поддержкой IPv6 в туннеле. [Диагностика файрвола OPNsense](https://docs.opnsense.org/manual/diagnostics_firewall.html)

## Диагностика

### Домен перестал резолвиться

Сравнить ответ одного и того же имени на трёх портах.

```sh
drill -p 5353 rr1---sn-35153iuxa-unxk.googlevideo.com @127.0.0.1 A
drill -p 53053 rr1---sn-35153iuxa-unxk.googlevideo.com @127.0.0.1 A
drill -p 53 rr1---sn-35153iuxa-unxk.googlevideo.com @127.0.0.1 A
```

| Результат | Что проверить |
| --- | --- |
| `5353` отвечает, `53053` возвращает `SERVFAIL` | В **Dnsmasq → Domains** проверить upstream `127.0.0.1:5353`. Применить запись и повторить запрос напрямую к Dnsmasq. |
| `53053` не отвечает | Проверить **Enable**, **Listen Port** и выбранный интерфейс в Dnsmasq. |
| `53053` отвечает, `53` возвращает ошибку | Проверить отдельную запись в **Unbound → Query Forwarding**. Если Unbound слушает DNS только на LAN-адресе, использовать этот адрес в проверке. |
| Ошибка уже на `5353` | Проверить локальный DoH-клиент и его внешний резолвер. |

В нашем случае `5353` вернул `NOERROR` и `178.91.255.76` за 12 мс, а `53053` вернул `SERVFAIL` примерно через 10 секунд. После переключения upstream Dnsmasq на `127.0.0.1:5353` разрешение домена и воспроизведение восстановились. Точная причина таймаута при обращении к прежнему upstream осталась неизвестной.

Проверить, слушает ли Dnsmasq, и увидеть обмен с DoH-клиентом можно такими командами. Во время захвата повторить запрос к Dnsmasq в другом терминале.

```sh
sockstat -4 -l -p 53053
tcpdump -ni lo0 'port 5353 or port 53053'
```

### DNS отвечает, но алиас пустой

Проверить тип `External (advanced)`, выбранный **Firewall Alias** в **Dnsmasq → Domains** и применение изменений. Сделать новый запрос к поддомену через Unbound и ещё раз посмотреть таблицу. У браузера может быть старый DNS-ответ в кеше. Если браузер использует внешний DoH, сравнить его адрес назначения с ответом локального Unbound.

### IP есть в алиасе, но потока в туннеле нет

Проверить входящий интерфейс, источник, порядок правил и выбранный gateway. Запустить новое соединение, чтобы исключить сохранённое состояние старого соединения. При необходимости найти состояние конкретного потока в **Firewall → Diagnostics → States**. Для проверяемого запроса сравнить фактический IP назначения и версию IP с полями правила. [OPNsense Firewall Diagnostics](https://docs.opnsense.org/manual/diagnostics_firewall.html)

### Сравнение с исходными алиасами

Чтобы подтвердить, почему один CDN работал, а другой выпадал, проверить оба исходных алиаса. `pfctl -T test` учитывает и одиночные IP, и попадание в подсеть.

```sh
pfctl -t PROXYDomains -T test 178.91.255.76
pfctl -t runetfreedomBlockList -T test 178.91.255.76
```

Статический GitHub-список может помочь с отдельными адресами. Например, `google-all/ipv4_merged.txt` содержал `178.91.255.76/31`. Если этот источник добавлялся в `runetfreedomBlockList` только для YouTube, после проверки `YouTubeCDN` можно убрать этот URL и проверить остальные маршруты. [Список `google-all`](https://github.com/you-oops-dev/ipranges/blob/main/google-all/ipv4_merged.txt)

### Проверка через SOCKS того же Xray

Эта проверка полезна, когда нужно отделить работу VPN от правил на входе клиентской сети. При доступном SSH-форвардинге открыть на ПК локальный порт до SOCKS на OPNsense. В команду подставить свой SSH-логин и LAN-адрес роутера.

```sh
ssh -N -o ExitOnForwardFailure=yes \
  -L 127.0.0.1:10880:127.0.0.1:10808 USER@OPNSENSE_LAN_IP
```

Оставить SSH-соединение открытым. На Linux в другом терминале запустить отдельный Chrome с SOCKS и открыть тот же ролик.

```sh
google-chrome --user-data-dir="$(mktemp -d)" \
  --proxy-server="socks5://127.0.0.1:10880" \
  --disable-quic https://www.youtube.com/
```

Если ролик играет, цепочка Xray передаёт видео по TCP через SOCKS. Браузер в этом режиме передаёт имя через SOCKS, поэтому DNS и выбор CDN могут отличаться от обычного запуска. Проверка `curl` на корне CDN по пути `/` может вернуть `HTTP 404` даже при исправном соединении. Воспроизведение проверяется реальным `videoplayback`.

## Как откатить изменения

1. В **Unbound → Query Forwarding** выключить только запись `googlevideo.com → 127.0.0.1:53053` и нажать **Apply**. Запросы к домену вернутся к общей схеме DNS.
2. Убрать `YouTubeCDN` из правила с `XRAYOUT` или выключить отдельное правило для этого алиаса. Применить настройки.
3. Если Dnsmasq включался специально для этого алиаса, его можно отключить в **General** после отката перенаправления.
